🧪 ChromaDB

A tiny vector database, start to finish

1 files124 lines shown22 MCQs14 glossary terms0%

In one breath

This folder has a single 124-line file. It builds a tiny database that stores meaning instead of rows, drops 14 grocery phrases into it, and then asks: "which three items are closest in meaning to the word apple?" That is the whole idea behind every RAG (retrieval-augmented generation) system in this repository - only the size changes.

  • Create a collection - a named bucket that knows how to turn text into numbers.
  • Fill it with short texts plus a small label (metadata) for each.
  • Query it with plain English and get back the nearest matches, with a distance for each.

Think of a kirana shop's stock register

A traditional shopkeeper writes items in a register: item 1 = apples, item 2 = bananas. To find something you must read every line, and you only find it if the spelling matches.

A vector database is the modern version of that register. The shopkeeper first writes a description card for every item (384 numbers describing taste, colour, type). Now if a customer says "something red and fruity", the shopkeeper does not need the exact word - they compare descriptions and hand over the three closest cards: apples, red fruit, golden apple.

That is why "golden apple" is found even though it does not contain the word "fresh". Similarity is measured on meaning, not spelling.

Think of an IRCTC enquiry counter

You ask an enquiry clerk: "Which train from Kanpur reaches Delhi before 9 am?" A good clerk does not memorise every timetable - they open the register, find the three relevant rows, and explain them to you. That is retrieval-augmented generation: the register is the vector database, the clerk is the LLM, and the answer is only as good as the rows they picked.

The files in this folder are the different ways of searching that register:

  • Self-query - "only trains departing after 6 pm" - filter first, then search.
  • Parent-document - search by the index card, then hand you the whole file.

The long docstring: what a handshake test is

This explains the single biggest beginner trap with watsonx.ai: most failures are credential or region problems, not code bugs. Read this once - the rest of the file is just the code version of it.

WHY THIS FILE EXISTS
--------------------
Almost every failure a beginner hits with watsonx.ai is NOT a code bug. It is one
of a small set of credential/account problems that all look similar from the
outside ("it doesn't work"). This script deliberately walks the credential chain
one link at a time so that the *first* thing that breaks is printed on its own,
with the exception type and the raw message from IBM.
 
WHAT "HANDSHAKE" MEANS HERE
--------------------------
1Talking to watsonx.ai is a multi-step negotiation, not a single API call:
 
    1. Your API key is exchanged for a short-lived IAM bearer token.
       (IBM's Identity and Access Management service issues the token.)
    2. That token is used to resolve the *project* you named, proving both that
       the project exists and that your account is allowed to use it.
    3. Only then is the actual model invocation sent.
 
If any link is broken the call fails, but the error text tells you which one.
A successful "generation" (step 3) is therefore proof that steps 1 and 2 also
succeeded - that is what makes this a genuine end-to-end handshake test.
 
THE TWO STAGES
--------------
Stage 1 goes through ``ibm-watsonx-ai``, the low-level SDK that LangChain itself
calls under the hood. Stage 2 goes through ``langchain-ibm``, the LangChain
wrapper. Running both isolates *where* a problem lives:
 
  * Stage 1 fails  -> credentials, region, project, or model access are wrong.
                      Nothing about LangChain is at fault. Fix stage 1 first.
  * Stage 1 passes,

                      is LangChain-level integration or versioning. A very
                      common cause is a version mismatch: the API surface of
                      ``langchain-ibm`` changes between releases (see the note
                      on ``WatsonxLLM`` further down).

unambiguous: you never have to guess whether the second error is a new problem
or just the first problem wearing a hat.

----------------------

    at the bottom of this file, so the script can be used as a health check in a
    pipeline (``if script; then ...``).
    """
28    settings = read_settings()

    # must be the region the project actually lives in.

In one breath

A two-file food search engine. shared_functions.py turns a 5,000-line JSON catalogue of dishes into a searchable vector index and answers natural-language queries - including requests a vector search alone cannot honour, like "desserts with the lowest calories" or "Thai food under 300 calories". interactive_search.py wraps that engine in a friendly command-line chatbot.

  • Stage 1-3: load JSON, repair missing fields, create a ChromaDB collection, embed every dish as one rich sentence.
  • Stage 4: two search functions - plain semantic, and semantic plus metadata filters (cuisine_type, calories <= N).
  • Stage 5: a tiny rule-based parser that reads "lowest", "under 300", "thai" from the query and re-ranks the results.

Think of a Zomato search that actually listens

You type "sweet baked dessert, lowest calories". A dumb search matches the words and returns the sweetest, heaviest cake. A good recommender does three things: it understands what you meant (dessert, sweet, baked), it respects your constraint (least calories), and it still shows only dessert-ish dishes - not a 3-calorie packet of vinegar that happens to be the lowest-calorie item in the catalogue.

That last point is the clever bit in this folder. Instead of sorting the whole catalogue by calories, perform_calorie_aware_search first collects about fifty semantically relevant dishes, then sorts that shortlist by calories. Relevance first, numbers second.

Analogy: a waiter first shortlists the dessert counter, then picks the lightest three from that counter - rather than handing you the lightest item in the whole kitchen.

    Args:

       :func:`perform_similarity_search` (no behaviour change, no extra cost).
    2. Retrieve a wider *semantic* candidate pool (``candidate_pool`` hits) using
       :func:`perform_filtered_similarity_search`, so cuisine/calorie limits are
       applied inside ChromaDB.
    3. If the user asked for the *lowest* calories, sort **that candidate pool**
       by calories ascending and keep the best ``n_results``.

    absolute lowest items are condiments (Vinegar 3 kcal, Pickles 5 kcal), which
    answer "lowest calories" but not "lowest-calorie dessert".  Sorting the
    semantically relevant pool keeps the result both on topic and correctly
    ordered.

            dessert query.

In one breath

A complete little web product: an HTML chat page, a JavaScript front end that posts your message, a Flask server that picks one of three watsonx models, and a Pydantic schema that forces every model to answer with the same three fields - summary, sentiment, response. Two extra scripts (capital.py, llm_test.py) show how to call the same models without any web layer.

Who talks to whomBrowser (index.html + script.js) -> POST /generate -> app.py -> model.py -> watsonx. The answer travels back the same path as JSON.
Why structured outputInstead of hoping the model writes JSON, you give it a schema. The library injects the schema, validates the reply and converts it into a Python object. No string parsing, no json.loads on model prose.

Think of a coaching-class notice board

Students (the browser) do not walk into the principal's office (the model) directly. They fill a form and drop it at the front desk (Flask). The desk checks the form is complete, decides which teacher should answer, carries the question in, and pins the answer back on the board in a fixed format so everyone can read it.

  • Front desk = the two Flask routes. One hands out the notice board, one accepts a form.
  • Form validation = if not user_message or not model plus the 400 status code.
  • Fixed answer format = the AIResponse Pydantic model.
  • Three teachers = Llama, Granite and Mistral - same question, different styles.
