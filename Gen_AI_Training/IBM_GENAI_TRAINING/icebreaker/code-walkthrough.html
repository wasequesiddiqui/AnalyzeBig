01

The big idea, in one minute

The bot does not memorise LinkedIn profiles and it does not fine-tune a model. It performs a trick called retrieval-augmented generation (RAG): it fetches the profile, cuts it into small pieces, converts each piece into numbers a computer can compare, and at question time hands the most relevant pieces to a language model as background reading.

STEP 1

Fetch

A profile dictionary arrives — from a mock JSON file or from the Proxycurl API.

STEP 2

Chop

The dictionary becomes JSON text, then gets split into 500-token chunks called nodes.

STEP 3

Embed

Each chunk is turned into a list of numbers (an embedding) that captures its meaning.

STEP 4

Ask

The question is embedded too; the five closest chunks are handed to the LLM, which writes the answer.

The library analogy

Imagine a huge library with no card catalogue. You take every page of a person's biography, glue each page onto its own index card, and file the cards by what they mean rather than alphabetically. When someone asks “what did this person study?”, you don't reread the whole book — you pull the five cards that feel closest to the question and read only those. That is exactly what a vector index does, and it is why the bot can answer without loading an entire profile into the model.

Why not just paste the whole profile into the model?

Because models have a limited context window, profiles can be long, and sending everything is slower and more expensive. Retrieval narrows thousands of words down to the few hundred that matter for the question — like a research assistant who has already highlighted the useful paragraphs before you start reading.

Credentials & model names constants ›

Four values are read at startup: the regional watsonx endpoint, the project ID, the LLM model name, and the embedding model name. The Proxycurl key is the fifth, but it is optional — without it the app quietly runs on mock data.

The one line that decides how the app starts

os.environ["WATSONX_PROJECT_ID"] is a hard requirement. Square brackets mean “give me this or crash”. os.getenv(...), used for the Proxycurl key, means “give me this, or just hand me None”. That single difference is why a missing Proxycurl key is harmless while a missing project ID kills the program instantly.

Step by step

  1. WATSONX_URL is hardcoded to the Frankfurt (eu-de) region.
  2. WATSONX_PROJECT_ID is pulled from the environment; missing → KeyError during import.
  3. LLM_MODEL_ID defaults to ibm/granite-4-h-small.
  4. EMBEDDING_MODEL_ID defaults to the multilingual Granite embedding model.
  5. PROXYCURL_API_KEY strips spaces and turns an empty string into None.
RequiredWATSONX_PROJECT_ID
OptionalPROXYCURL_API_KEY
OverridableLLM_MODEL_ID at runtime
Why this matters: the Proxycurl key used to be missing entirely, which crashed main.py with AttributeError. Defining it as optional fixed the mock-mode path: no key → no API call → no crash.

Tuning knobs & prompt templates constants ›

These numbers decide how the models behave, and the two template strings decide what they are asked to do. They are deliberately kept in one place so you can experiment without touching the logic.

What each number controls

  1. SIMILARITY_TOP_K = 5 — retrieve the five most relevant chunks per question.
  2. TEMPERATURE = 0.0 — ask for near-deterministic, factual wording.
  3. MAX_NEW_TOKENS = 500 / MIN_NEW_TOKENS = 1 — length limits for the answer.
  4. TOP_K = 50, TOP_P = 1 — sampling breadth (how adventurous word choice is).
  5. CHUNK_SIZE = 500 — how large each text chunk is when splitting the profile.

The templates use named holes

{context_str} is replaced by the retrieved profile chunks and {query_str} by the user's question. LlamaIndex fills both automatically. The wording also instructs the model to admit ignorance rather than invent facts — a simple, important guard against hallucination.

lookup_profile() http ›

Performs one GET request and converts the nested JSON into a flat, predictable shape the rest of the code could use without knowing the API's original layout.

Think of it like…

A translator at a hotel desk. The guest speaks in a complicated dialect (nested JSON); the translator hands you a short, standard form with exactly the fields you asked for.

Step by step

  1. requests.get(url, timeout=15) asks the server for user number 1.
  2. raise_for_status() converts any 4xx or 5xx response into an exception — no silent failures.
  3. response.json() parses the JSON body into a Python dictionary.
  4. profile.get("company", {}).get("name") digs two levels deep safely.
  5. The result is returned as a new dictionary with a nested location.

def lookup_profile():
    url = "https://jsonplaceholder.typicode.com/users/1"
    response = requests.get(url, timeout=15)
    response.raise_for_status()
    profile = response.json()

    return {
        "name": profile.get("name"),
        "username": profile.get("username"),
        "email": profile.get("email"),
        "company": profile.get("company", {}).get("name"),
        "website": profile.get("website"),
        "location": {
            "city": profile.get("address", {}).get("city"),
            "zipcode": profile.get("address", {}).get("zipcode"),
        },
    }

logging configuration (module level) setup ›

Before anything else, the script configures the root logger to print time - name - level - message lines to standard output at INFO level.

Why not just print()?

Because log lines carry a severity and a source name, can be filtered, and can be sent to a file later without changing every call site. print is for the user; logging is for the developer.

Step by step

  1. basicConfig sets the global level and format (only the first call has effect).
  2. A StreamHandler sends records to sys.stdout.
  3. logger = logging.getLogger(__name__) creates a named logger for this file.
Subtle: run the file directly and __name__ is "__main__", so the logger is called __main__. Import it and the same logger is called main. That is why log lines can show either name.
Affects every logger.* call in every module

process_linkedin(linkedin_url, api_key=None, mock=False) orchestration ›

The whole pipeline in one function: fetch → split → embed → verify → summarise → chat. Each stage's result is checked before the next stage runs, so a failure stops the chain with a clear log line.

Think of it like…

A recipe with quality checks. If the shop has no ingredients (no profile data), you stop before chopping. If the oven will not heat (no index), you stop before baking.

Step by step

  1. extract_linkedin_profile(...) returns a dict, or {} on failure.
  2. if not profile_data — an empty dict is falsy, so the function logs and returns.
  3. split_profile_data turns the dict into a list of text nodes.
  4. create_vector_database embeds those nodes and returns an index (or None).
  5. verify_embeddings checks the index; a False result only logs a warning — the code continues.
  6. generate_initial_facts asks the LLM for three facts, which are printed.
  7. chatbot_interface(index) takes over for free-form questions.
ReturnsNone (it acts, it does not return data)
On errorLogs the exception and returns quietly
NetworkYes — profile fetch + embedding + LLM
Trade-off: the single except Exception at the bottom keeps the app friendly, but it also hides bugs. You see a log line, not a stack trace — so debugging means reading the log carefully.
Calls extract · split · create index · verify · generate facts · chatbot · Called by main()
def process_linkedin(linkedin_url, api_key=None, mock=False):
    try:
        profile_data = extract_linkedin_profile(linkedin_url, api_key, mock=mock)
        if not profile_data:
            logger.error("Failed to retrieve profile data.")
            return

        nodes = split_profile_data(profile_data)
        vectordb_index = create_vector_database(nodes)
        if not vectordb_index:
            logger.error("Failed to create vector database.")
            return

        if not verify_embeddings(vectordb_index):
            logger.warning("Some embeddings may be missing or invalid.")

        initial_facts = generate_initial_facts(vectordb_index)
        print("\nHere are 3 interesting facts about this person:")
        print(initial_facts)

        chatbot_interface(vectordb_index)
    except Exception as e:
        logger.error(f"Error occurred: {str(e)}")
chatbot_interface(index) chat loop ›

A blocking while True loop that reads a question, shows a fake “typing…” pause, asks the query engine, and prints the answer. It ends only on an exit word.

Think of it like…

A shop counter that stays open until you say “goodbye”. Each customer (question) is served completely before the next one arrives.

Step by step

  1. input("You: ") blocks until the user types something.
  2. If the text is exit, quit or bye, print a farewell and break.
  3. Print “Bot is typing…”, flush, sleep one second, then erase the line.
  4. answer_user_query(index, user_query) returns a LlamaIndex response object.
  5. response.response.strip() extracts the answer text and prints it.
ReturnsNothing; ends on an exit word
BlocksYes — waits on input()
StateKeeps the same index for every question
Fragile spot: on failure answer_user_query returns a plain string, and strings have no .response attribute. The chat loop would raise AttributeError — and this function has no try/except, so the program ends.

def chatbot_interface(index):
    print("\nYou can now ask more in-depth questions ...")
    while True:
        user_query = input("You: ")
        if user_query.lower() in ['exit', 'quit', 'bye']:
            print("Bot: Goodbye!")
            break

        print("Bot is typing...", end='')
        sys.stdout.flush()
        time.sleep(1)
        print('\r', end='')

        response = answer_user_query(index, user_query)
        print(f"Bot: {response.response.strip()}\n")

create_watsonx_embedding() factory ›

Builds a WatsonxEmbeddings object configured with the endpoint, project, and embedding model from config, then returns it.

What an embedding model does

It turns a sentence into a long list of numbers — a fingerprint of meaning. Two sentences about similar things get similar fingerprints, which is what makes search by meaning possible instead of search by exact word.

Step by step

  1. Reads config.EMBEDDING_MODEL_ID, WATSONX_URL and WATSONX_PROJECT_ID.
  2. Passes truncate_input_tokens=3 — the maximum number of input tokens the service is asked to accept.
  3. Returns the object; no network call happens until text is actually embedded.
ReturnsWatsonxEmbeddings
RaisesOn bad configuration or credentials
Review flag: a cap of 3 tokens is tiny — almost any real sentence is longer. This value looks like a leftover experiment rather than an intentional setting.

def verify_embeddings(index):
    try:
        vector_store = index._storage_context.vector_store
        node_ids = list(index.index_struct.nodes_dict.keys())
        missing_embeddings = False

        for node_id in node_ids:
            embedding = vector_store.get(node_id)
            if embedding is None:
                logger.warning(f"Node ID {node_id} has a None embedding.")
                missing_embeddings = True

        return not missing_embeddings
    except Exception as e:
        logger.error(f"Error in verify_embeddings: {e}")
        return False

def answer_user_query(index, user_query):
    try:
        watsonx_llm = create_watsonx_llm(

05

Concepts, slowly

Every term the code uses, explained without assuming prior AI knowledge. Open the ones you need — each card ends with the concrete place in this project where the idea appears.

Retrieval-augmented generation (RAG)

Instead of asking a model to remember facts, you give it the relevant facts in the prompt. “Retrieval” finds the useful pages; “generation” writes the answer from them.

This is why the bot can talk about a person the model has never seen: the knowledge lives in the retrieved chunks, not in the model's training.

Here: index → retrieve top 5 → fill {context_str} → LLM answers

Embedding

A list of numbers that represents the meaning of a piece of text. Texts with similar meaning end up with similar lists — even if they share no words.

The embedding model in config.py converts each chunk into one of these lists.

“engineer” and “developer” land near each other; “banana” lands far away

Vector / similarity search

Once text becomes numbers, “find related text” becomes “find the nearest lists”. The vector store compares the question's embedding with every stored embedding and returns the closest matches.

This is why you get conceptually related results rather than exact keyword matches.

Here: VectorStoreIndex in create_vector_database()

Chunk and node

A chunk is a slice of the profile text; LlamaIndex calls the wrapped slice a node. Smaller pieces retrieve more precisely, but too small and you lose context.

Overlap (200 tokens by default here) repeats a little text at the edges so ideas are not sliced in half.

Here: SentenceSplitter(chunk_size=500)

Top-k retrieval

“k” is how many nearest chunks you keep. With top_k = 5, the model sees the five best-matching chunks — a balance between enough context and too much noise.

Higher k means more background but a longer, slower, costlier prompt.

Here: config.SIMILARITY_TOP_K = 5

Prompt template

A string with named holes. LlamaIndex fills {context_str} with retrieved text and {query_str} with the user's question before sending it to the model.

Templates are how you give instructions — tone, limits, and “say I don't know when the context lacks the answer”.

Here: INITIAL_FACTS_TEMPLATE and USER_QUESTION_TEMPLATE

Temperature

A randomness dial. 0.0 means “pick the most predictable wording”; higher values allow more variety and creativity — and more risk of drifting from the facts.

For a factual résumé assistant, low temperature is the right default; for brainstorming, raise it.

Here: config.TEMPERATURE = 0.0

Greedy vs sampling decoding

Greedy always takes the single most likely next word, so output is stable. Sampling draws from a probability distribution, so output varies between runs.

This project uses sampling for the three facts and greedy for user questions — a small inconsistency you can see in query_engine.py.

Here: decoding_method="sample" vs "greedy"

max_new_tokens

An upper limit on how many tokens the model may generate. It stops runaway answers and controls cost and latency. A token is roughly a word fragment — “icebreaker” is about two or three.

Here: 500 for facts, 250 for answers

Environment variables and .env

Key–value settings that live outside the code, so secrets never get committed. A .env file holds them locally; load_dotenv copies them into the process environment.

WATSONX_PROJECT_ID=... · PROXYCURL_API_KEY=...

Command-line arguments

Values typed after the script name, parsed by argparse. Flags start with --; a flag like --mock stores True when present.

python main.py --url "..." --model "ibm/granite-4-h-small"

Logging vs print

print is for the person using the program; logging is for whoever maintains it. Log records carry a severity and a source, so warnings can be filtered without deleting code.

Here: pipeline diagnostics use logger, conversation uses print

Sentinels instead of exceptions

Every module catches its own exceptions and returns a special “nothing worked” value: {}, [], None or False. The caller then checks it with if not result.

This keeps a demo friendly, but it trades away error detail — you must read the logs to know what actually failed.

Here: return [], return None, return False

Honest review notes

Reading code critically is a skill. These are real rough edges in the current files — each one is a chance to see how small design decisions create bigger consequences.

highThe API key never reaches the request

modules/data_extraction.py · line ~146

The header is {"Authorization": f"******"} — a masked literal, not f"Bearer {api_key}". A key is required, checked, then ignored, so live Proxycurl calls cannot authenticate. The function's own docstring admits this.

highTwo different return types from one function

modules/query_engine.py · answer_user_query

Success returns a response object; failure returns a plain string. The caller does response.response.strip(), so the failure path raises AttributeError and kills the chat loop.

mediumMissing project ID crashes at import

config.py · line ~13

os.environ["WATSONX_PROJECT_ID"] raises KeyError when the variable is absent, before main() runs. Using os.getenv plus an explicit error message would be friendlier.

mediumexcept Exception everywhere

all modules

Useful for a classroom demo, risky in production: bugs, typos and credential problems all collapse into “returned None”. Nothing propagates, so tests cannot fail loudly.

mediumA three-token embedding cap

modules/llm_interface.py · truncate_input_tokens=3

That parameter is the maximum number of input tokens accepted. A value of 3 would truncate almost any sentence, which likely hurts embedding quality. It looks like a leftover experiment.

lowDead context_str and double retrieval

modules/query_engine.py · answer_user_query

The code retrieves the top 5 nodes, joins them into context_str, then never uses it — and the query engine retrieves the same nodes again. Removing both lines would be faster and clearer.

lowDefaults frozen at import time

modules/llm_interface.py · create_watsonx_llm

temperature=config.TEMPERATURE is evaluated once, when the module loads. Changing config.TEMPERATURE later changes nothing. Pass the value explicitly if it must vary.

lowReaching into private attributes

modules/data_processing.py · verify_embeddings

index._storage_context is an internal LlamaIndex detail. The check works today but may break on upgrade; the public storage-context API would be safer.

lowA “test” file that never tests

test_config.py

It prints values instead of asserting them, so pytest reports zero tests. Renaming it would stop pytest collecting it at all; adding assert statements would make it useful.
