Planned Upgrades

STOCK_REACT_ASSIST · upgrade registry & design decisions

static/PlannedUpgrades.html

This file is the backlog

It exists so that a planned upgrade can be discussed once, recorded precisely, and then implemented later — by a human or an assistant — without the reasoning being lost.

The machine-readable part is <script type="application/json" id="upgrade-registry"> further down this file. Everything rendered on this page is derived from that block, so the numbers on screen cannot drift away from the data.

02

Status vocabulary

applies to every entry
StatusMeaningAction expected
planned Agreed and fully specified. Ready to implement. Implement when its dependsOn entries are done.
in-progress Work has started but verification has not passed. Continue; do not start a competing entry in the same area.
done Implemented and every verification item passed. Nothing — but dependsOn references to it are now unblocked.
candidate Captured as a real possibility, deliberately unscheduled. Ask before starting. Never implement silently.
rejected Considered and declined, with the reason recorded. Do not implement. Do not re-propose without new evidence.

06

How to use this file

instructions for a future session

If you are an assistant being asked to implement a planned upgrade, read this tab before touching any code.

Operating instructions

read first
READ THIS FIRST if you are an assistant asked to work on planned upgrades. 1. PARSE THE REGISTRY. Read the JSON inside <script type="application/json" id="upgrade-registry">. It is the single source of truth. Do not infer the backlog from prose on this page. 2. SELECT WORK. Take entries whose status is "planned" and whose dependsOn ids are all "done". Respect priority order (P0 before P1 before P2). "candidate" entries are deliberately unscheduled - ask before starting one. Never start a "rejected" entry. 3. READ THE ENTRY FULLY before touching code. "problem" says why, "recommendedApproach" says how, "steps" are ordered and each names its files and symbols, "verification" is the gate you must pass. 4. DO NOT RE-LITIGATE "alternativesRejected". Each option there was considered and declined, with a reason and a date. If you believe one is now correct, say so and ask - never silently switch approach. 5. RESOLVE "openQuestions" with the user if the answer changes the design. 6. IMPLEMENT THE STEPS IN ORDER. A step's dependsOn means the earlier step must land first. Do not batch unrelated steps into one sprawling edit. 7. RUN EVERY ITEM UNDER "verification". These are not suggestions. An entry is not complete until they pass. If a check is impossible in the current environment, say so explicitly rather than skipping it silently. 8. KEEP THIS FILE IN SYNC. Flip "status", append an entry to "discussion" with the date and the outcome, and bump "meta.updated". Nothing else in the project tracks upgrade state. Update the JSON only - every count on this page is derived, so never hand-edit a number. 9. DO NOT EDIT PROJECT SOURCE AS A SIDE EFFECT of editing this page. Creating or updating a plan is a separate, deliberate act from implementing it. 10. PRESERVE THE INVARIANTS named in "decisions". They encode choices that were hard to reach, and the most likely failure mode of this work is an assistant quietly undoing one.

Editing rules for the JSON block

gotchas
  • No raw newlines inside a string. A JSON string value must sit on one line. This is the same class of failure that blanked AllFunctionList.html when a multi-line value was written inside its JS array literal.
  • No double quotes inside a string value. Refer to code with <code> styling in the surrounding page instead — the renderer escapes text, so it is safe to write < and &.
  • Keep it valid JSON. After any edit, run get_errors on this file and reload; a syntax error renders every derived panel as empty rather than throwing a visible error.
  • Never hardcode a count anywhere in the page. Stat cards, the header chip, the registry counter and the row totals are all computed from the registry.

Element schema

reference
meta: project string - project name purpose string - one-line reason this file exists updated string - ISO date, bumped on every edit readerNote string - the instruction aimed at a future assistant upgrades[]: id string - stable key, e.g. "U1". Referenced by dependsOn. title string status string - planned | in-progress | done | candidate | rejected priority string - P0 | P1 | P2 | P3 | "-" area string - grouping, e.g. "Vectorless RAG / Retrieval" effort string - S | M | L | "-" dependsOn string[] - ids of other upgrades; a gate, not a hint summary string - what the upgrade is, in one paragraph problem string - why it is needed recommendedApproach string - how it should be done alternativesRejected { name, why }[] - decided against; do not re-open steps[] { n, detail, files[], symbols[], dependsOn[] } verification[] string[] risks[] string[] decisions[] { date?, text } openQuestions[] string[] acceptanceCriteria[] string[] discussion[] { date, who, text } - append-only log
